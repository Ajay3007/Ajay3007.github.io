Why the kernel is slow for packets 👇 (and how DPDK hits line rate)

A 10 GbE link can deliver ~14.8 MILLION packets per second. Send each one through the Linux kernel and you'll never keep up. Here's the tax every packet pays on the normal path:

1) 🔔 Interrupt — the NIC fires an IRQ; the CPU stops what it's doing to service it
2) 📋 Copy — the packet is copied into a kernel sk_buff, and the whole TCP/IP stack runs
3) 🔁 Context switch — control flips from kernel to your app in user space
4) 📋 Copy AGAIN — into your buffer, on recv()

Per-packet interrupts + copies + syscalls = the kernel tops out around ~0.5 Mpps.

DPDK's move: bypass the kernel completely. 🚀
• the NIC DMAs packets straight into your process's memory (hugepage-backed mempool)
• a poll-mode driver busy-polls the card — no interrupts
• the packet is a pointer you read in place — zero copy, no syscalls

Result: ~0.5 Mpps → ~15 Mpps PER CORE.

The catch: a whole core spins at 100% polling, and you lose the kernel's networking stack — you rebuild what you need in user space. For routers, firewalls, and load balancers at line rate, that's the trade you make.

Skip the kernel → reach line rate.

-- Title --
Why the Kernel Is Slow for Packets (and How DPDK Bypasses It)

-- Description --
The Linux kernel is a general-purpose networking stack — and that generality is exactly why it can't keep up with a 10/40/100 GbE link. This first episode of the High-Performance Data Plane series follows a single packet up the normal kernel path and shows where the time goes, then contrasts it with DPDK's kernel-bypass approach.

The kernel path, per packet:
1. Interrupt (IRQ): the NIC signals the CPU, which stops its current work to run the interrupt handler.
2. Copy + stack: the packet lands in a kernel buffer (sk_buff) and the TCP/IP stack processes it.
3. Context switch: control moves from kernel space to your application in user space.
4. Second copy: recv() copies the data again into your buffer.

Multiply interrupts, copies, and syscalls by ~15 million packets per second and the kernel saturates around half a million packets per second.

DPDK's kernel bypass:
- The NIC DMAs packets directly into a hugepage-backed mempool in user space.
- A poll-mode driver (PMD) busy-polls the NIC rings instead of taking interrupts.
- Your code reads the packet in place — it's just a pointer (mbuf). No copies, no syscalls, no context switches.

That takes throughput from ~0.5 Mpps to tens of Mpps per core. The trade-offs: a CPU core spins at 100% polling, and you give up the kernel's networking stack, so you implement what you need yourself. That's the deal that powers software routers, firewalls, and load balancers at line rate.

⏱️ ~0.5 Mpps (kernel) → ~15 Mpps/core (DPDK)
